# Native Linux and macOS telemetry slice (experimental)

`tbme-native-probe` is the first platform-native, read-only TaskbarMonitorEnhanced sensor component for Linux and macOS. It is **not yet a complete desktop application**, installer or system tray/taskbar UI. Neither the Windows application nor immutable v1.7.10 release changes.

Build on Linux or macOS with a native C++17 compiler:

```sh
c++ -std=c++17 -O2 -Wall -Wextra -Werror -pedantic native/telemetry/main.cpp -o tbme-native-probe
./tbme-native-probe --self-test
./tbme-native-probe --once
```

The JSON schema 1 response exposes sampled system CPU usage (200 ms), memory total and available in **bytes**, `cpuTemperatureC:null` and `temperatureAvailable:false`. Missing counters fail closed with nonzero exit instead of invented readings. Linux reads the kernel's `/proc/stat` and `/proc/meminfo`. macOS uses the native Mach host statistics API and `sysctlbyname("hw.memsize")`. macOS available memory is an approximation, **not** a substitute for memory pressure. No sudo, third-party dependency or background service required.

CI compiles and runs both targets on independent hosted Ubuntu/macOS, validates JSON types, bounds and intentional unsupported-argument refusal. Acceptance applies only to this telemetry slice; native GPU/thermal service, UI, packaging, persistence, autostart, configuration and end-user tests remain open.

## Bounded NDJSON streaming

Use **./tbme-native-probe --samples 3** to emit exactly three complete JSON lines, one after a kernel counter sample lasting at least 200 ms (up to 2 s if the native host returns unchanged counters). Each line is flushed to stdout for future UI integration. The sample count must be decimal digits in the inclusive range 1..60; invalid counts exit 2 without telemetry output. Sensor read failures exit 3; output write failures exit 4. The original --once and --self-test contracts stay backward compatible. This bounded CLI is not a background daemon, desktop app, installer, or UI acceptance.
## Experimental platform-native desktop UIs

Both UI components use the same read-only native/telemetry/sample.hpp adapter as the tested CLI. Linux uses GTK3 GtkApplication/GtkApplicationWindow and a 2-second GLib timer, displaying CPU and approximate used RAM percentages in a small standalone native window. macOS uses AppKit NSStatusBar/NSStatusItem and NSTimer to show the same values in a status item menu. Neither UI launches a shell, invokes an untrusted executable, installs a background process, reads user settings, or elevates privileges.

Linux build in a desktop session with GTK3 headers/runtime:

    c++ -std=c++17 -O2 -Wall -Wextra -Werror -pedantic native/linux/Panel.cpp -o tbme-linux-panel $(pkg-config --cflags --libs gtk+-3.0)
    ./tbme-linux-panel --self-test
    ./tbme-linux-panel

macOS build on a Mac with Apple Command Line Tools/AppKit:

    clang++ -std=c++17 -O2 -fobjc-arc -Wall -Wextra -Werror -pedantic native/macos/StatusBar.mm -framework AppKit -framework Foundation -o tbme-macos-status
    ./tbme-macos-status --self-test
    ./tbme-macos-status

These are developer builds, not signed/distributed packages. Hosted Linux Xvfb only verifies that the GTK window can be created in an isolated X11 session; hosted macOS compiles and runs noninteractive sensor selftests without asserting a visible status item. A real owner Linux/Wayland/X11 desktop, macOS logged-in GUI, accessibility, multiscreen behavior, settings, Glass appearance, thermal alerts/audio, native packaging and launch-at-login all remain unaccepted.

Reference interfaces: https://docs.gtk.org/gtk3/class.Application.html ; https://docs.gtk.org/glib/func.timeout_add_seconds.html ; https://developer.apple.com/documentation/appkit/nsstatusbar .
## Disposable unsigned packaging candidates

For a developer-only, explicitly new output path, the project provides native host builders. Neither builder installs, registers, autostarts, signs, notarizes, or publicly releases anything. They refuse to overwrite an existing target:

- On Linux with the GTK3 development environment and dpkg-deb, run **bash native/linux/build-preview-deb.sh /absolute/new/path/preview.deb**. It emits an unsigned Debian package containing a GTK3 binary and a desktop-entry file with a documented, provisional system GTK dependency. It is inspected in hosted CI without installation; its dependency/ABI compatibility and real owner install/uninstall behavior are not accepted.
- On macOS with AppKit/clang, run **bash native/macos/build-preview-app.sh /absolute/new/path/TaskbarMonitorEnhancedNativePreview.app**. It emits an unsigned standalone LSUIElement agent .app with a valid Info.plist and a native sensor-testable executable. No signing, Gatekeeper/notarization or user-session LaunchServices acceptance is asserted.

These experiments use preview version 0.1.0 (Linux Debian package revision r443), distinct from immutable Windows release 1.7.10. Full distribution remains blocked until genuine per-platform GUI/installation/upgrade/uninstall tests and release authorization.

Packaging references: https://developer.apple.com/library/archive/documentation/General/Reference/InfoPlistKeyReference/Articles/LaunchServicesKeys.html and https://www.debian.org/doc/debian-policy/ch-binary .

## R447 Linux CPU temperature opt-in hardware scope

The experimental native CLI and GTK3 Linux preview can read the Linux kernel hwmon temperature interface as a read-only, best-effort CPU sensor. The adapter checks only known CPU-related drivers (coretemp, k10temp, zenpower, peci_cputemp, cpu_thermal, x86_pkg_temp), preferring Intel CPU package readings or AMD Tdie over AMD Tctl, and explicitly refuses GPU amdgpu, motherboard acpitz, invalid numbers, unknown labels or impossible 0..150 C range violations. The kernel sysfs value is millidegrees Celsius; Tctl on AMD is a temperature-control indicator and may differ from actual die temperature. No synthetic temperature or default zero is emitted. See https://docs.kernel.org/hwmon/sysfs-interface.html and https://docs.kernel.org/hwmon/coretemp.html .

The NDJSON schema 1 retains the existing cpuTemperatureC numeric-or-null and temperatureAvailable boolean fields and adds the optional source identifier cpuTemperatureSensor (a static allowlisted string or null). macOS remains explicitly temperature unavailable. The Linux GTK3 preview displays the source label and value only when a recognized real CPU sensor exists; no alarm or configurable alert threshold is asserted. Synthetic filesystem fixtures test driver allowlist, source preference, invalid values and GPU exclusion; independent owner Ubuntu detection is tested separately. The reported temperature is a driver-exposed sensor reading, not a calibrated absolute junction measurement, and it does not establish thermal-alert product parity.
### Read-only thermal witness from a native executable

For independent hardware acceptance on Linux, run tbme-linux-panel --probe-temperature from the unsigned preview package in a local extracted directory. This reads the same allowlisted hwmon sensor used by the GTK3 label, returns one line in the form 56.375 k10temp:Tctl when an actual supported sensor is present, and returns exit code 3 with no stdout if unavailable. The command never launches GTK, calls a shell or requires administrator privileges. A successful real-hardware witness does not establish calibration or an audible alarm. The measured Tctl control temperature must remain identified as Tctl and must not be labeled as a physical die temperature.
## R448 Native Linux opt-in thermal-warning settings

The experimental Linux GTK3 panel offers an advisory visual high-CPU-temperature warning and an independently opt-in system bell request. Both are disabled by default; no sound is requested on normal launch. Users can enable the warning, set the CPU temperature threshold between 50 and 110 degrees C (default 85), and independently enable the system bell. The warning uses an explicit HIGH CPU TEMPERATURE label and GTK3 CSS red/bold class (not color alone), 3 degrees C reset hysteresis, and a monotonic 60-second minimum between repeated bell requests. gdk_display_beep() asks the desktop display to sound the system bell; an audible sound is not guaranteed and no physical owner audio acceptance is claimed. Do not treat this as an automatic safety shutdown, calibrated junction-temperature alarm or replacement for firmware thermal protection. k10temp:Tctl is a thermal control indicator and must retain that source label.

Settings are stored only after explicit user interaction or a command-line mutation in the per-user XDG_CONFIG_HOME/taskbarmonitorenhanced-native-preview/settings.ini (normally under ~/.config). The program never modifies Windows owner settings or the public v1.7.10 release. Writes use GLib atomic durable replacement, owner-only creation mode 0600, preserve unrelated valid INI keys, reject oversized/non-regular/symlinked files and directories, and fail closed on malformed preferences rather than overwriting them. The GUI disables settings controls when an existing configuration is invalid. This is a Linux developer preview feature, not yet a stable settings schema or full cross-platform migration contract. Relevant upstream references: https://docs.gtk.org/glib/func.file_set_contents_full.html , https://docs.gtk.org/glib/func.get_user_config_dir.html , https://docs.gtk.org/gtk3/class.CssProvider.html .

Headless Linux smoke commands for a new, disposable XDG_CONFIG_HOME:

    export XDG_CONFIG_HOME="$(mktemp -d)"
    ./tbme-linux-panel --settings
    ./tbme-linux-panel --set-alert true
    ./tbme-linux-panel --set-threshold 90
    ./tbme-linux-panel --set-bell false
    ./tbme-linux-panel --settings

The tests in native/linux/test-native-settings.cpp validate safe defaults, persistence, restrictive file modes, corrupt-file refusal, invalid bounds, symlink refusal, hysteresis, no sound when disabled or temperature unavailable, and 60-second bell throttling. CI also creates a synthetic pre-existing user preference file in an isolated runner temp folder and checks it survives the developer preview .deb upgrade, same-version reinstall, remove and purge. None of these proves an upgrade from a public Linux release or a physical system bell. Host display testing and owner user-session acceptance remain separate.
## R449 macOS native AppKit refresh preference

The unsigned developer-only native macOS AppKit status item now exposes a Refresh interval submenu with 2, 5 or 10 second options (default 2), selected-state checkmarks and live rescheduling of its native NSTimer; it does not launch an external helper. A dedicated per-user NSUserDefaults suite (com.god13emad.taskbarmonitorenhanced.nativepreview.settings) stores the selection after explicit user interaction. A malformed saved interval causes the headless settings read to return code 3; the GUI safely uses 2 seconds at runtime without rewriting the malformed value until the user actively chooses a menu item. Noninteractive preview commands are --settings and --set-interval 2/5/10; invalid values are refused.

The GitHub-hosted disposable macOS runner builds the AppKit source, performs real per-process preference read/write/re-read and invalid input refusal, then packages the unsigned .app and validates the archive roundtrip. This verifies macOS native Foundation preferences code and CLI only, NOT a logged-in macOS status-menu GUI interaction, real hardware compatibility, installer upgrade/recovery, signing/notarization, user acceptance or CPU thermal/audio functionality. Linux native alert settings are a distinct platform implementation and are not yet shared with macOS.
## R449 GTK3 hosted Xvfb startup-order correction

The GitHub-hosted Ubuntu native UI smoke test intermittently failed after compiling the same working Linux source: the previous command started a DBus session before Xvfb, so the session portal could initialize before DISPLAY existed. This ordering had previously been reproduced and corrected in the independent owner Ubuntu lab (R444). Hosted regression failure in run 43282980841, job 131408871363, occurred AFTER Linux settings fixture, GTK compilation and CLI settings contract all succeeded, but before the GTK3 Xvfb marker. The CI harness now starts isolated Xvfb first, then a new DBus session, runs the native window with GDK_BACKEND=x11 and GTK_USE_PORTAL=0, verifies window discovery with a bounded wait and checks for an early process exit. Diagnostic output is printed only on failure. This is a CI display/session setup correction, not proof of a product GUI root cause or primary desktop acceptance.
### R449 preference-suite isolation correction

A distinct NSUserDefaults suite identifier ending in .nativepreview.settings is deliberately different from the experimental AppKit bundle CFBundleIdentifier (.nativepreview). Apple advises not passing the application bundle identifier to initWithSuiteName. The source also avoids deprecated manual synchronize calls; per-process readback of a set value is checked and the CI verifies independent command invocations. This verifies only disposable-host preference behavior, not the owner GUI or guaranteed immediate disk persistence in a power-loss scenario. References: https://developer.apple.com/documentation/foundation/userdefaults/init(suitename:) and https://developer.apple.com/documentation/foundation/userdefaults/synchronize() .
## R450 explicit malformed Linux settings recovery (opt-in; original retained)

The R448 Linux GTK3 panel correctly refused an invalid INI settings file, but disabled the warning controls and offered no in-app recovery. R450 adds a visible Recover invalid settings button only when initial settings parsing failed, and a noninteractive --recover-settings command. Both explicitly recover **only a malformed regular file** up to 4096 bytes, within the same user-owned XDG location; valid or absent settings are never replaced. A single, fixed settings.ini.rejected hard-link archive is created before any overwrite using link() with no-clobber semantics, then the malformed source path is detached and a new 0600 settings.ini is durably written with visual and bell warnings OFF, threshold 85 C. This retains the malformed original bytes (also when it was previously unreadable), without creating versioned piles of backups. Recovery refuses existing archive, symlinks, multi-hardlinked/non-regular and oversized paths, or a modified inode during the operation. On failure after archive creation it retains original evidence and attempts to restore only an absent original path; no data-loss-free guarantee is claimed under concurrent same-user attacker modification or filesystem failure. The user can inspect the one retained .rejected file before deleting it manually.

R450 Linux unit and headless GTK CLI tests check that an invalid file fails closed, recovery explicitly preserves exact bytes, reset starts with warnings OFF, second recovery cannot overwrite the archive, valid settings are refused, and symlink settings cannot be recovered. The CI operates in an entirely disposable XDG_CONFIG_HOME; no real owner settings or system installation are touched. The GTK recovery UI still needs independent Xvfb accessibility and genuine owner desktop acceptance; a recovered settings file is not proof of a physically audible temperature alarm.
## R451 thermal warning bell cooldown across transient readings

R448 originally cleared lastBellSecond both when a CPU temperature sensor was unavailable and when CPU temperature cooled at least 3 C below the warning threshold. That permitted another advisory GDK display-bell request immediately after any cool/hot oscillation or sensor dropout, bypassing the documented minimum 60-second cooldown. R451 keeps the timestamp of the last bell request for the entire process lifetime even if thermal readings become unavailable, the warning visual latch cools off, or the user switches alerts off/on or changes the threshold. Only the visual high-temperature latch is re-armed when alert/threshold settings change; it does not reset audio throttling. Monotonic time is used to prevent wall-clock adjustments from resetting cadence. Invalid/missing values remain fail-closed. The unit regression exercises repeated hot/cool, sensor dropout, enable/disable, threshold increase, the 59s negative boundary and exactly 60s next request; Ubuntu CI requires the R451 marker. This is a sound-request scheduling guarantee within one running preview process, not a guaranteed heard sound or a safety shutdown. Relaunching the application creates a new in-memory cooldown state; process-to-process bell cadence and physical audio acceptance are NOT claimed. No audio output is played by tests.
## R453 macOS preference numeric type and corruption regression

The experimental macOS AppKit refresh interval loader previously called NSNumber.integerValue on a persisted setting, which silently truncates malformed fractional numeric values (e.g. 2.5 to 2) into a supported interval. The loader now reads a finite double and accepts only exactly 2, 5, or 10 seconds; invalid, non-NSNumber, and out-of-range values refuse CLI --settings (exit code 3), and the menu uses a safe 2-second runtime fallback without silently overwriting the invalid file. The user can explicitly repair it by choosing an interval in the menu or using --set-interval. The disposable macOS GitHub runner now writes fractional and string preference fixtures through the native defaults tool, verifies both are rejected in independent processes, then explicitly repairs and confirms persistence. These checks are headless settings tests, not a real logged-in macOS menu acceptance. Runner-side test preferences are nonproduction; installed owner Windows settings and the Linux XDG schema are untouched.
